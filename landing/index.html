Deleted customers

A stale background job can quietly bring a deleted customer back, with no error and no alert. DeleteProof reproduces that race on demand, shows exactly why it happens, and proves the fix.

The problem

A ghost-write: the bug most teams find in production.

A sync job is queued, then the customer is deleted. When the job finally runs, its upsert sees no row, so it inserts one. The deleted customer is back, and every tool says everything is fine.

t0

Customer exists

An active row in customers.

t1

Sync job queued

A BullMQ job carries a stale profile update.

t2

Deletion commits

The API deletes the row. Right-to-erasure honored… for now.

t3

Customer is back

The worker's upsert inserts a fresh row from the stale payload.

The invariant we protect Once a deletion commits, no background job may recreate that customer.

How it works

From "it happens sometimes" to a pass/fail verdict in one command.

Real PostgreSQL 17, real Redis 7, a real Fastify API and BullMQ worker. No mocks, no sleep timers.

01

Reproduce

Redis barriers (LPUSH/BLPOP) pause each process at the exact point needed, so the race happens every run.

02

Explain

A merged trace from the API and worker shows which transaction wrote after the delete committed.

03

Repair

A tombstone plus a per-customer advisory lock, so a delete and a stale write can never overlap.

04

Verify

Five scenarios in both modes. The fix must block stale writes and keep real updates working.

The fix

Two changes, one transaction.

Why not just check whether the customer exists first? Because the delete can commit between the check and the write. The lock closes that gap; the tombstone remembers the deletion.

worker · vulnerable.tsRESURRECTS
INSERT INTO customers (id, email, name, profile)
VALUES ($1, $2, $3, $4)
ON CONFLICT (id) DO UPDATE  SET profile = customers.profile
              || EXCLUDED.profile;

-- Row was deleted, so there is no conflict.
-- The INSERT branch runs and the customer returns.
worker · fixed.tsINVARIANT HELD
BEGIN ISOLATION LEVEL READ COMMITTED;
SELECT pg_advisory_xact_lock(customer_lock_key(id));SELECT 1 FROM customer_tombstones
 WHERE customer_id = id;
-- found → COMMIT, write skipped
-- not found → upsert → COMMIT
COMMIT;

Quick start

Break it yourself in under a minute.

# infrastructure (or: npm run services:up — no Docker needed)
docker compose up -d
npm install && npm run migrate

# one API + one worker
npm run start:api
npm run start:worker

# watch the ghost-write, then the fix
npm run dp -- run --scenario delayed-update-after-delete --mode vulnerable
npm run dp -- run --scenario delayed-update-after-delete --mode fixed
